# Day 7 – AI Storage Structure Documentation

## 1. Objective

The objective of this document is to define how different types of data are organized and stored across the Zecpath AI recruitment platform.

The design covers original resumes, parsed candidate profiles, parsed job profiles, ATS scores, screening reports, interview results, and final hiring decisions.

The proposed formats use original files for raw documents and JSON for structured records. These are design specifications; not every record type is currently implemented or stored by the application.

## 2. Proposed Folder Structure

```text
data/
├── raw/
│   ├── resumes/
│   └── job_descriptions/
│
├── parsed/
│   ├── candidate_profiles/
│   └── job_profiles/
│
├── ats_scores/
├── screening_reports/
├── interview_results/
├── hiring_decisions/
├── datasets/
│   ├── training/
│   ├── validation/
│   └── testing/
└── schemas/
```

### Folder descriptions

- `raw/resumes/`: Original candidate resume files.
- `raw/job_descriptions/`: Original job description files.
- `parsed/candidate_profiles/`: Structured candidate profiles extracted from resumes.
- `parsed/job_profiles/`: Structured job requirements extracted from job descriptions.
- `ats_scores/`: Candidate-job matching scores and related metadata.
- `screening_reports/`: Screening findings and skill matching results.
- `interview_results/`: Interview evaluations and feedback.
- `hiring_decisions/`: Authorized final hiring outcomes.
- `datasets/`: Versioned datasets prepared for model training and evaluation.
- `schemas/`: JSON schema definitions for validating structured records.

This is a proposed logical storage structure. It can be implemented incrementally without moving the existing Day 4 and Day 6 files immediately.

## 3. Resume Storage

Original resumes should be preserved in their uploaded format, such as PDF or DOCX. The original document should be kept separate from the extracted text and parsed profile.

Suggested location:

`data/raw/resumes/`

Example filename:

`CAND001_resume.pdf`

The filename is illustrative. Candidate identifiers should be generated by the application and should not contain unnecessary personal information.

## 4. Parsed Candidate Profile

Parsed profiles store the information extracted from a resume.

Example JSON:

```json
{
  "record_id": "PROFILE001",
  "candidate_id": "CAND001",
  "created_at": "2026-10-13T08:00:00Z",
  "updated_at": "2026-10-13T08:00:00Z",
  "schema_version": "1.0",
  "parser_version": "resume-parser-1.0",
  "processing_status": "processed",
  "skills": [
    "Python",
    "SQL"
  ],
  "education": [],
  "experience": [],
  "source_file": "CAND001_resume.pdf"
}
```

The example demonstrates a proposed storage format. The current resume parser does not necessarily extract or populate every field shown here.

## 5. Parsed Job Profile

Job profiles contain the structured requirements extracted from job descriptions.

Example JSON:

```json
{
  "record_id": "JOBPROFILE001",
  "job_id": "JOB001",
  "created_at": "2026-10-13T08:00:00Z",
  "schema_version": "1.0",
  "parser_version": "jd-parser-1.0",
  "job_title": "Python Developer",
  "required_skills": [
    "python",
    "sql",
    "rest apis",
    "git"
  ],
  "preferred_skills": [
    "fastapi",
    "docker",
    "aws"
  ],
  "experience_required": {
    "minimum_years": 1,
    "maximum_years": 3
  },
  "processing_status": "processed"
}
```

The values are based on the sample Python Developer job description. The additional metadata fields are part of the proposed storage design.

## 6. ATS Score Storage

ATS records should capture a candidate's matching score against a specific job.

Example JSON:

```json
{
  "record_id": "ATS001",
  "candidate_id": "CAND001",
  "job_id": "JOB001",
  "created_at": "2026-10-13T08:10:00Z",
  "scoring_version": "ats-rules-1.0",
  "score": 82.5,
  "score_scale": "0-100",
  "status": "completed"
}
```

The score is illustrative, not an actual result from the current application.

Each score must identify both the candidate and the job because one candidate may apply for several jobs, and one job may have several candidates.

## 7. Screening Report Storage

Screening reports should contain the results of candidate screening, including matched skills, missing skills, findings, and processing information.

Example JSON:

```json
{
  "record_id": "SCREEN001",
  "candidate_id": "CAND001",
  "job_id": "JOB001",
  "created_at": "2026-10-13T08:15:00Z",
  "screening_version": "screening-rules-1.0",
  "matched_skills": [
    "Python",
    "SQL"
  ],
  "missing_skills": [
    "Docker"
  ],
  "status": "completed"
}
```

The example is a proposed record format. The matched and missing skills must come from actual screening results when the format is implemented.

## 8. Interview Result Storage

Interview records should preserve evaluation results and link them to the relevant candidate and job.

Example JSON:

```json
{
  "record_id": "INTERVIEW001",
  "candidate_id": "CAND001",
  "job_id": "JOB001",
  "created_at": "2026-10-13T09:00:00Z",
  "evaluation_version": "interview-rules-1.0",
  "status": "completed",
  "evaluation": {
    "technical_score": null,
    "communication_score": null,
    "feedback": []
  }
}
```

Null scores indicate that no score has been recorded in this example. Interview evaluations should be based on documented criteria and reviewed according to the organization's hiring policy.

## 9. Hiring Decision Storage

The final hiring decision should be stored separately from individual AI scores and screening reports.

Example JSON:

```json
{
  "record_id": "DECISION001",
  "candidate_id": "CAND001",
  "job_id": "JOB001",
  "created_at": "2026-10-13T10:00:00Z",
  "decision": "pending",
  "decision_maker_id": null,
  "supporting_records": [
    "ATS001",
    "SCREEN001",
    "INTERVIEW001"
  ]
}
```

This is a proposed format. AI scores should support the hiring process rather than automatically determine the final decision. Authorized personnel should record the final outcome.

## 10. Data Relationships

The primary relationships are:

- One candidate can have multiple parsed profile versions.
- One job can have multiple candidate applications.
- Each ATS score links a candidate to a particular job.
- Screening reports link to the candidate and job being evaluated.
- Interview results link to the relevant candidate and job.
- A hiring decision references the supporting assessment records.

Stable IDs allow the platform to connect these records without duplicating the entire resume or job description in every output.

## 11. Data Retention and Security

Candidate resumes, interview feedback, and hiring decisions contain sensitive information.

The system should implement:

- Role-based access controls.
- Secure storage and transfer.
- Defined retention and deletion policies.
- Validation before data is accepted.
- Audit trails for changes to important records.
- Separation of identifying information from training datasets where appropriate.

Training data should be used only under approved organizational policies and applicable privacy requirements.

## 12. Conclusion

This storage structure defines a consistent proposed format for raw documents, parsed profiles, ATS scores, screening reports, interview results, and hiring decisions.

The use of stable identifiers, JSON records, version fields, and timestamps will support traceability and future integration across the Zecpath AI recruitment platform.

The design can initially use local files and JSON records, with migration to a database or object storage when the application's requirements justify it.
